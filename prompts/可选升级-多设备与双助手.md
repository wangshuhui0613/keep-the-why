# 可选升级：多设备与多助手共同维护

> **这一步是可选的。** 单机使用完全不需要它。
>
> 只有当你开始用两台以上电脑，或者同时让多个 AI 助手维护同一个库时，才需要配这一层。
> 提前配它，只会让你在还没形成使用习惯的时候，先花两小时调同步。

## 什么时候该配

| 信号 | 说明 |
|---|---|
| 你在公司和家里各有一台电脑 | 两边都要写，靠 U 盘拷必然丢内容 |
| 你同时用两个以上 AI 助手 | 它们各自不知道对方改了什么 |
| 你担心本地硬盘坏了 | 知识库这类东西丢了是补不回来的 |

## 怎么用

确认基础版已经跑顺之后，把下面代码块里的内容整段复制给你的 AI 助手。
它会先给出计划，**不会直接动手**。

```text
请在现有知识库已通过基础验证的前提下，为我设计并配置「私有 GitHub + 多设备 / 多助手共同维护」模式。

开始前先读取现有 README.md、AGENTS.md 和使用说明，不得重建或覆盖知识库。涉及 GitHub 登录、建库、授权和首次推送时暂停，让我本人确认。

协作规则必须满足：
1. GitHub main 是跨设备交换知识的唯一中枢，仓库必须为私有；
2. 顺序固定为：检查本地状态 → 拉取并合并远端 → 修改 → 验证 → 提交 → 推送；
3. 冲突优先合并双方内容，无法判断时保留两版并让我决定；
4. 禁止强制推送、硬重置或丢弃另一方改动；
5. 删除已有文件或大段内容前必须让我确认；
6. 共享脚本放在 tools/，本机状态目录（.workbuddy/、.obsidian/workspace.json）不进入 Git；
7. 双链使用完整相对路径且不带 .md 后缀；
8. 多个助手分时增量沉淀新增对话，更新已有项目或主题文件，不重复创建每日聊天摘要；
9. 同步前运行结构、断链、敏感信息和敏感信息检查；
10. 自动化失败、冲突或删除风险出现时停止，不得为了「同步成功」牺牲内容。

先给出将新增或修改的文件、自动任务时间和验证方式。得到我确认后再执行。
```

## 这一层真正的难点

不是 `git` 命令，是**纪律**：

- **先拉后推。** 每次推送前先 `fetch` + `pull`，把远端合并进来再推自己的。被拒绝通常不是故障，只是说明远端有新提交。
- **冲突不覆盖。** 合并冲突看不懂时，把两版都留下来交给未来的自己判断，比"选一个看起来对的"安全得多。
- **本机状态不共享。** `workspace.json` 这种界面状态进了共享库，两台电脑会互相打架。
- **自动化失败就停。** 定时同步任务报错时，让它停在那儿等人看，不要为了"今天同步成功"而牺牲内容。

## 相关的坑（提前知道能省几小时）

| 现象 | 真实原因 |
|---|---|
| `git push` 一直失败，只说 "failed to push some refs" | 大概率是远端有你本地没有的提交，先 pull；也可能是 pre-push 钩子依赖的工具没装好 |
| 两台电脑统计数字对不上 | 某台把本机缓存目录也算进去了，检查 `.gitignore` |
| 定时同步任务"明明建了却没跑" | 创建时间晚于当天的触发点，第一次执行会排到第二天，不是故障 |
| 大文件推不上去 | 超过 100MB 需要 Git LFS，注意 LFS 随工具升级可能被覆盖丢失 |
